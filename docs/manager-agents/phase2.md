# Phase 2 — Website UI Monitor

19 October 2026. Implemented across Studio/relay and the sibling `MAPI/Sleeper-cell-main` Android source. The separate phone **Website UI monitoring** preference is off by default. The source implementation was initially validated locally. The user subsequently installed GitHub Actions APK 1.0.128, and the compatible production relay was deployed for pilot validation; see the installed-phone section in [validation](validation.md#phase-2-installed-phone-check). Existing Phase 1 reporting remains enabled and healthy.

## Observation and reporting

One phone-local observer covers ChatGPT, Gemini and Google AI Studio. It reads existing WebViews on page/history transitions, return to the browser and relevant automation lookup failures. A read-only probe exports six categories of controls: composer, send, upload, model selection, navigation and response actions. It retains presence/ambiguity, allowlisted labels, coarse location and appearance/icon fingerprints. It excludes conversation/prompt/response text, HTML, full URLs, account names and screenshots.

The [manifest](website-ui/manifest.json) documents supported composer, upload-menu, model-menu and response-action states and provisional resource limits. It is a selector catalogue, not a set of preaccepted website baselines. Every new provider/page/viewport/locale/theme/profile scope starts without a baseline. Profile variant is explicitly unknown; local profile references and exact evidence keep impacts scoped. Matching baseline/change signatures can group devices without marking unobserved variants incompatible.

Loading, streaming, keyboard, known session/quota overlays and unsupported dialogs are unchecked. Suspected changes require another comparable observation at least two seconds later to become confirmed; duplicate/old observations cannot supply confirmation. Missing/ambiguous required controls are routed initially as suspected and then blocking when confirmed. Label/icon/style/location changes with recognized, intact controls are informational. Other control structure changes produce compatibility warnings. Normal conversation updates do not enter the fingerprint.

The path is **Website UI Monitor → same phone's Device Image Clipper Manager → Issues Manager → user**. The phone's additive SQLite journal migration (version 1 → 2) stores baseline/variant state, change history and delivery correlation alongside existing durable outbox events. Local manager acceptance and forwarding intent commit together. The forwarding source is `device_clipping`, not `website_ui`; the receiving protocol rejects a direct Monitor-to-Issues incident shortcut. The relay's acceptance transaction creates/updates the durable incident, and its receipt is recorded locally in the same transaction that removes the delivered outbox item.

`manager-report/1` gains optional versioned `website-ui/1` evidence and a `website_ui` stage. Producers leave Issues receipt time empty. Studio derives it only from accepted forwarded reports, including a previously optimistic record after offline delivery. Original producer payloads remain immutable. Old strict receivers reject this extension, so deployment order and the default-off phone flag are required.

All confirmed changes, including cosmetic changes without failed clipping, create an actionable notification with appropriate severity. Repeated delivery and multiple devices update one change group while retaining source/profile impacts. Acknowledging an incident does not replace its baseline, verify compatibility or resolve it.

## Owner controls and audits

Sleeper-Cell → Tools → Settings → Cloudflare R2 contains the monitoring switch and **Website UI status and baselines**. The screen lists observed scopes, missing baselines, control evidence and manager receipts. **Accept this observed baseline** records explicit owner review of that exact evidence; missing/ambiguous required controls prevent acceptance. **Verify required controls** is a separate action and requires a stable, matching observation no more than two minutes old. Returning to the existing browser page refreshes evidence without navigation. Verification can resolve prior changes for the same accepted variant; it does not claim a test generation was executed.

Idle audits inspect at most two existing live tabs per minute, with a provisional 24-hour due interval. No suspended tab is created/loaded, no profile is selected and no prompt/upload is submitted. Audits due during work are reported deferred. Unvisited pages remain unchecked. Active-work page/failure observations remain passive and leave existing recovery behavior intact. There is no adapter self-repair, task dispatch or automatic baseline replacement.

Studio's Production Issues page adds provider coverage, stale/due states, variant details, expected/observed controls and both handoff receipts. UI incidents link to that evidence. Phone Status also links to UI status. Legacy runners supply active workflow impact but do not yet provide durable task IDs; task-level ownership remains Phase 3 work.

## Validation and release boundary

See [validation](validation.md#phase-2-source-validation). Constructed redacted fixtures cover all three providers; Kotlin generates reports consumed by TypeScript and the isolated relay. DOM probe tests use a controlled VM document fixture, not a live website browser. Local relay tests cover grouping, informational notifications, rejected shortcut, acknowledgment/verification separation and replay after process restart. Android JVM tests cover classification, all supported required-control states, variants, redaction, duplicate ordering and owner review. Android SQLite code compiles; real device crash/offline instrumentation remains pending.

The Nord ChatGPT composer scope has passed live required-control detection and owner review on 1.0.128. Other account/device/provider variants, raster-only visual differences, runtime overhead and full visual QA have not been validated for this release. Unsupported dialogs/page variants remain unchecked. A structurally verified control set does not prove a generation/upload succeeds. Audit limits are provisional until measured on the pilot. There is one global monitoring switch; finer per-provider/variant threshold controls remain a rollout refinement. Existing pending changes and baselines are preserved when reporting is disabled.

Release in this order: deploy compatible relay/Studio, build/release Android using GitHub Actions, install that release, enable monitoring on one idle pilot device, observe each supported provider page, explicitly review its baseline and verify controls, then verify a harmless controlled change/offline replay and measure overhead. The earlier installed 1.0.126 production evidence remains Phase 1 evidence. APK 1.0.128 packaging and continued reporting have now been checked; the observed ChatGPT composer scope now has a live stable observation, explicit owner baseline acceptance and separate required-control verification accepted by production and visible in Studio. Other provider scopes and the remaining failure/overhead checks are still pending.

Rollback by turning off Website UI monitoring, retaining the compatible journal and relay records. Existing outbox handoffs may still finish through Manager observations; to stop all new report delivery, disable Manager observations too. Do not delete pending reports or downgrade a version-2 journal into the older version-1-only APK. No automatic production recovery is introduced by this phase.
